# CPU-only benchmark notes — 2026-10-31

Environment: Windows 11, Docker Desktop on WSL2, 12 logical threads, no GPU.
Worker used `DETECTOR_BACKEND=onnx` with YOLOv5n at 640×640. The load generator
ran inside the Compose network to avoid host-network overhead.

## Load tests

| Scenario | Workers | Published | Processed | Stale/dropped | p50 | p95 | p99 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 4 streams, 10 FPS target, 60 s | 1 | 888 | 158 | 730 (82.2%) | 468.4 ms | 806.1 ms | 876.6 ms |
| 2 streams, 3 FPS target, 60 s | 2 | 354 | 259 | 95 (26.8%) | 440.4 ms | 710.9 ms | 798.6 ms |

The 4-stream generator produced only ~15 FPS aggregate on this CPU, so that run
is an overload/backpressure test rather than a valid 40 FPS NFR measurement.
The 2-stream run produced ~5.9 FPS aggregate and is a closer approximation of
the requested load.

## Reproduce

```bash
docker run --rm --network video-analytics_default \
  --entrypoint python \
  -v "$PWD/benchmarks:/bench:ro" \
  video-analytics-worker \
  /bench/load_test.py --redis-host redis --streams 4 --seconds 60 --fps 10
```

For the two-worker run, scale the worker service to 2, then use
`--streams 2 --seconds 60 --fps 3`. Adjust the network name if
`COMPOSE_PROJECT_NAME` is set.

## Conclusion

The pipeline bounds latency by shedding stale frames under overload. The PRD
target of 4 streams at 10 FPS with p95 <500 ms and <2% drops is **not met** on
this CPU-only setup. A GPU backend or a smaller model is required for that
target.
